# 개발 중 반복된 문제와 교훈

같은 실수를 두 번 하지 않기 위한 문서다. 사용자에게 보이는 실패 문구의 원인은 `docs/TROUBLESHOOTING.md` 에 따로 적는다.
새 실수를 하면 그 세션에 아래 "kube-sim 에서" 에 추가한다. 같은 실수가 두 번이면 규칙(테스트·AGENTS.md)으로 막는다.

## net-sim 에서 물려받은 것 (자세한 사연은 `../net-sim/docs/LESSONS.md`)

### 설계
- 큰 UI 를 만들기 전에 디자인 방향과 상호작용 모델을 먼저 보여 주고 확인받는다. 첫 버전이 "내가 바란 게 아니다" 를 받았다.
- 설정이 바뀌면 그 설정에서 파생된 상태를 무효화한다(쿠버네티스라면: 템플릿이 바뀌면 새 ReplicaSet, Service 셀렉터가 바뀌면 엔드포인트 재계산).
- 모델 → 코어 diff 동기화는 **처리 순서가 곧 의미**다(지우기 전에 알릴 것을 먼저).
- 시계가 조용할 때 멈추는 구조에서는 끝나지 않는 주기 타이머를 일반 타이머로 넣으면 시계가 영원히 뛴다 → 배경 타이머. 주기 동작이 상대에게 일으키는 일반 타이머 사슬의 길이도 따진다(4s).
- 동기 콜백·재진입이 끼는 곳은 **상태 갱신·등록을 먼저, 송신·통지는 마지막에**(세 번 어김 — 4h·4k).
- 기다리는 상태에는 반드시 끝(timeout)을, 서로를 가리킬 수 있는 구성에는 홉·횟수 상한을 둔다.
- 링크·오브젝트 변화를 하나씩 받아 바로 결정하면 "같은 순간의 다른 변화" 를 못 본다 → 0ms 뒤에 모아서 결정(4v).
- 파생 상태를 매번 처음부터 다시 계산하면 새 항목 하나가 기존 배정을 흔든다 → 기존 배정을 먼저 지키고 남는 것만 새로(4v).
- 실제 프로토콜·시스템이 이미 답을 가진 문제는 그 답을 구현한다. 표준의 "왜" 를 빼고 옮기면 그 이유가 버그로 돌아온다(4i).
- 옆에 있는 비슷한 기능의 리뷰 결함 목록을 새 기능을 만들기 전에 체크리스트로 대조한다(4u).
- 설정 변경 = 재시작이 기본이면 켜기만 해도 장애가 난다. "무엇이 바뀌었나" 별로 다르게 처리한다(4r).

### 도구 (Preact + Vite + Playwright)
- Preact signals: `effect` 안에서 `sig.value += 1` 은 Cycle detected → `sig.value = sig.peek() + 1`.
- 전역 CSS 클래스는 컴포넌트 접두어를 붙인다(`.empty`·`.summary` 충돌로 화면이 두 번 깨졌다). 새 클래스 이름은 grep 으로 먼저 확인.
- Playwright: SVG 텍스트는 `textContent()`, Preact 입력값은 프로퍼티라 `evaluateAll(e => e.value)`, `text=문구` 대신 `button:has-text()`, 섹션은 제목(`h3`)으로, 장치는 이름 칸이 정확히 같은 것으로 찾는다. 토스트가 사라질 때까지 기다린다. 움직이는 대상을 누르는 단계는 가끔 놓친다(다시 돌려 보고, 되풀이되면 고친다).
- 검증 스크립트는 Vite 를 별도 포트(5199)로 직접 띄운다. 사용자 프로세스는 건드리지 않는다.
- Bash 도구는 제어 문자가 든 명령을 거부한다 → 긴 파일은 파일 쓰기 도구로.
- 성능은 개발 서버가 아니라 프로덕션 빌드로 잰다. 체감 버벅임은 fps 보다 움직임의 연속성(이름표 튐)부터 의심한다.

### 테스트·검증
- 시나리오는 `runToIdle()` 로 안정화한 뒤, 트레이스는 동작 전 길이를 기록하고 `slice(before)` 로 단언한다. 요약문이 아니라 `kind` 시퀀스로 단언한다.
- 분산·반복 동작은 **종료성**을 따로 검증한다(여러 모양에서 `runToIdle` 이 한도 안에 끝나는지).
- 큰 기능 뒤 깨끗한 문맥의 리뷰 에이전트에게 재현 테스트로 결함을 찾게 하면 매번 실제 결함이 나왔다(한 번에 7~20건). 손실·중복·늦게 온 메시지·"한쪽만 초기화"·같은 순간의 여러 변화를 꼭 시험하게 한다.
- 예제·화면을 바꾸면 스크린샷을 직접 본다. 테스트가 다 통과해도 겹침·잘림은 화면에서만 보인다.
- 리뷰 worktree 는 결과를 옮긴 뒤 지운다. `git add -A` 금지(worktree 가 gitlink 로 담긴다).

## kube-sim 에서
- (2026-10-02) 실제로 영원히 재시도하는 동작(ImagePullBackOff·CrashLoopBackOff)이 있는 시나리오에서 `runToIdle` 을 쓰면 상한까지 돌다 실패한다. 테스트는 `runFor(ms)` 로 시간을 정해 돌린다(ARCHITECTURE 1절 결정).
- (2026-10-02) 그리드 칸 안의 `white-space: nowrap` 줄은 칸을 넓혀 옆 내용(자원 숫자·IP)을 잘라 먹는다 → 그 칸에 `grid-template-columns: minmax(0, 1fr)`. 테스트는 통과했고 스크린샷에서만 보였다.
- (2026-10-02) 칩 안 한 줄에 상태·재시작·IP 를 다 넣으면 가장 중요한 상태 문구(CrashLoopBackOff)가 잘린다 → 오류 상태에서는 덜 중요한 것(IP)을 숨긴다.
- (2026-10-02) 첫 리뷰(재현 테스트 13건, 높음 0)는 대부분 "실제 출력과 다른 문구·표기" 였다: YAML 의 자원 단위(250 → 250m), `status: True` 따옴표, AGE 의 긴 구간, `delete` 출력·플래그, describe 의 NewReplicaSet. kubectl 흉내를 넓힐 때는 실제 kubectl 소스의 문구·규칙(HumanDuration, delete 의 --force/--grace-period 규칙, generateName 58자)을 먼저 확인한다.
- (2026-10-02) "모든 Node 변경에 스케줄 재시도" 는 kubelet 의 status.images 갱신에도 깨어나 이유 없는 FailedScheduling 을 또 찍었다 → 스케줄에 영향을 주는 속성(allocatable·cordon·taint·라벨·Ready)이 바뀔 때만, 그리고 트레이스에 재시도 이유를 남긴다.
- (2026-10-02) 예제의 "해 볼 것" 순서가 학습 포인트를 지운다(앞 단계가 Pending 을 없애 뒤 단계에서 볼 게 없음) → 예제 테스트는 순서대로 실행하며 각 단계의 전제(예: Pending 이 있는지)도 단언한다.
- (2026-10-02) 화면 시계를 "일반 이벤트가 있을 때만 흐름" 으로 정했더니 노드 장애(배경 타이머로만 진행 — heartbeat 끊김을 5초 주기 감시가 알아챔)가 영원히 일어나지 않았다. 시간이 흘러야만 생기는 일이 주제인 시뮬레이터는 배경 타이머도 시계를 흐르게 해야 한다. `runToIdle` 은 그대로 일반 이벤트만 본다.
- (2026-10-02) Pod 54개를 한꺼번에 만들면 긴 프레임(167ms, CPU 4배 감속)이 났다. 원인은 그림이 아니라 코어의 복사: 스케줄러·ReplicaSet 이 Pod 하나마다 전체 Pod 목록을 깊은 복사(O(n²))하고, watch 이벤트를 구독자마다 복사했다. 내부 읽기는 `api.peekList`(복사 없음, 읽기 전용), watch 이벤트는 복사본 하나를 공유 → 최악 조각 27ms → 6ms. 성능 문제는 짐작 말고 Node 에서 코어만 따로 재 본다.
- (2026-10-02) 서버가 정하는 값(ClusterIP·NodePort)을 "만들 때만" 정했더니, 바꾸는 경로(apply·인스펙터 편집)에서 type 을 NodePort 로 바꿔도 포트가 비었다. 서버가 정하거나 검사하는 필드는 create·update 양쪽에서 같은 함수로 처리한다(불변 필드 검사 포함).
- (2026-10-02) 도구 출력은 사용자가 친 것을 그대로 따라야 한다: curl 은 친 이름(web)을, NodePort 로 들어왔으면 NodePort 를, wget 이면 wget 문구를. 내부에서 풀린 값(FQDN·Service 포트)을 찍으면 학습자가 다른 것을 했다고 오해한다.
- (2026-10-02) 화면·스크립트에 손으로 적은 목록(ui-check 의 컨트롤 플레인 개수, perf-check 의 예제 목록)은 기능이 늘면 틀린다 → 코드에서 읽는다.
- (2026-10-02) kube-proxy 규칙 반영에 1초 지연을 넣자 "EndpointSlice 는 ready 인데 요청이 거부됨" 이 화면 검증에서 보였다 — 실제와 같은 지연이지만, 검증 스크립트·예제가 "막 뜬 직후" 를 기준으로 하면 틀린다. 지연을 새로 넣으면 그 지연을 건너는 검증을 모두 다시 본다.
- (2026-10-02) 오래 걸리는 작업(drain)의 끝 조건을 "지금 상태"(노드의 Pod 수 0)로 잡으면, 사용자가 도중에 다른 일을 하면(uncordon·Pod 삭제) 영원히 안 끝난다. 실제 도구처럼 "시작할 때 고른 대상" 으로 끝을 정하고, 기다리는 동안 늘 다음 확인을 걸어 둔다.
- (2026-10-02) 정리 작업(옛 ReplicaSet 삭제)을 매 reconcile 마다 돌리면 진행 중인 것을 지운다 — 실제 컨트롤러가 "끝난 뒤에만" 하는 일은 그 조건을 그대로 옮긴다.
- (2026-10-02) 화면 검증에서 문구를 includes 로 찾으면 "not ready 1" 이 "ready 1" 에 걸리고, 예제를 바꾼 직후에는 옛 예제의 같은 이름 요소에 걸린다 → 정확한 요소(data- 속성)와 시작·전체 일치로 찾는다.
- (2026-10-02) 실제 컨트롤러가 "다른 오브젝트의 변화" 로도 깨어나는 경우(IP 반납 → 기다리던 Service, 내가 만든 Deployment 삭제 → 오퍼레이터)를 빠뜨리면 상태가 굳는다. 컨트롤러를 만들 때 "무엇이 바뀌면 나를 다시 깨워야 하나" 를 목록으로 적고 watch 를 맞춘다.
- (2026-10-02) "끝없이 되풀이되는 자동 동작" 은 대개 "해도 아무것도 바뀌지 않는 동작을 조건 없이 다시 거는 것" 이었다 (prune 꺼진 selfHeal). 자동으로 다시 시도하는 곳은 "이번 시도가 무엇을 바꾸나" 를 먼저 보고, 바꿀 것이 없으면 시도하지 않는다.
- (2026-10-02) apply 를 spec 통째 교체로 만들면 다른 도구가 붙인 값(rollout restart 의 restartedAt)을 지운다 — kubectl apply 의 3-way merge(last-applied)를 흉내 낸다.
